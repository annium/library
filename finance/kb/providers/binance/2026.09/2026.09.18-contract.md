## Why this run happened

Step 5f's fourth stage placed a real `STOP_MARKET` on 2026-09-18 and the exchange refused it:

> `Order type not supported for this endpoint. Please use the Algo Order API endpoints instead.`

That was recorded as `contested` and handed back to steps 1-2 rather than guessed at. This run answers
it, and the answer turned out to be documented all along — in a file the previous run had already
fetched and stored.

## Step 1 — the manifest against the tree

Of **107 line-anchored facts, 76 resolved and 31 had moved**, clustering where steps 3 to 5 worked. No
cited file had disappeared. That is ordinary wear.

Three things were not ordinary.

**One entry asserted the opposite of the code.** §7 read "Nothing reads `Retry-After`". The code has
read it for some time — `HttpRequestRateExtensions.cs:121-125` — along with a regex over the exchange's
human-readable ban message. A manifest that contradicts the code it points at is the failure this
document exists to prevent, and it survived a full contract pass.

**One fact was recorded twice with opposite values.** The rate-limit decay constants were `none` in the
census table and `pinned` in §7. Neither was right: the step is pinned on USD-M in one direction only,
the interval is not pinned at all, and spot has no decay test.

**21 facts lived in the code and nowhere in the manifest.** The `Retry-After` read and the ban regex;
a second HTTP status map, narrower than the documented one, where `401`/`403`/`404` fall to
`UnknownError`; the Binance code `-1003`; the paging cursors `orderId` and `fromId`; the assumption
that history comes back sorted, carried by `.Last()` and stated only in a source comment; the reload
cadences that decide how much weighted traffic this module generates at rest.

**Three new `[DEAD]`:** both futures account events are registered and never resolved, and the
websocket control ack is parsed by nothing — we send `SUBSCRIBE` and never read the answer. The spot
user path is deader than recorded: its `UserProvider` issues no HTTP at all, so the spot converters,
enum tables and cancel-GUID rule beneath it are unreachable too.

**Four test defects**, queued for step 5 rather than fixed here: two `vacuous` assertions
(`positions.Count.IsGreaterOrEqual(0)`, which cannot fail; `SmallTables_MapEveryMemberBothWays`, whose
round trip holds by construction), a precision heuristic whose only untested branch is the one that
makes it a heuristic, and the listen-key lifecycle, where every exchange fact is replaced by a
synthetic stand-in so the component is covered and the contract it carries is not.

## Step 2 — what the documentation says

### The blocking finding, and it was not new

**Conditional orders migrated to a different endpoint family on 2025-12-09**, announced 2025-11-06 —
`usd-futures/change-log.md:729`. Affected: `STOP_MARKET`, `TAKE_PROFIT_MARKET`, `STOP`, `TAKE_PROFIT`
and `TRAILING_STOP_MARKET`. `POST /fapi/v1/order` and `POST /fapi/v1/batchOrders` now refuse them with
`-4120 STOP_ORDER_SWITCH_ALGO`, whose documented text (`usd-futures/error-code.md:52`-region) is our
observed text word for word.

**The endpoint is not the one the error message points at.** "Algo Order API" also names
`/sapi/v1/algo/futures/*`, a separate product for execution algorithms — TWAP and volume participation.
Conditional orders went to **`/fapi/v1/algoOrder`**, inside the same futures API. Following the error
message literally would have meant implementing the wrong product, which is precisely why the finding
was handed back to this layer instead of being acted on where it was found.

Request shape is `confirmed` at tier 1 from the Postman collection. Four field names change —
`algoType` appears and is required, `stopPrice` becomes `triggerPrice`, `newClientOrderId` becomes
`clientAlgoId`, `orderId` becomes `algoId` — and cancel no longer takes `symbol`. The announcement also
states three behavioural changes no parameter list would show: no margin check before trigger,
`GTE_GTC` now keyed on positions rather than opposing open orders, and **modification of an untriggered
conditional order is not supported**.

The full table is in `manifest.md` §5. What is still unknown is the **response** shape, including the
payload of the new `ALGO_UPDATE` stream event.

### The process finding, which matters more

**That text was in the 2026-09-01 snapshot.** Line 698 of the change-log file that run fetched and
stored, nine months after the migration took effect. The run read the changelog, followed a link out of
it to find a WebSocket migration notice, reported that — and missed this, sitting in the same file as
an ordinary bullet list.

So the gap was never retrieval. It was reading, and the cost of the gap was a live order refused by the
exchange, which is the most expensive way a contract question can be answered.

The skill was amended the same day, before the rest of this run continued. The change inverts the
direction of the check: **the corpus is not the unit of work, our facts are.** Reading a vendor's
documentation and asking what matters is unbounded and unauditable; the manifest is a bounded,
enumerable set, so for each fact of ours we go and find where their documentation confirms it. Three
mechanical sweeps — grep the snapshot for every wire literal we hold, sweep the changelogs for dates
read against today, diff the endpoint inventory — run before anything is read by judgment. And an
outcome now requires a citation: without one the entry is `unchecked`, whatever the reader believes.

Measured on the file that hid it: `STOP_MARKET` has **nine** hits in the 107 KB changelog, and the date
sweep produces **31** entries. Both are readable in minutes. It was never a question of effort.

### The retrieval gap the previous run recorded as impossible

`developers.binance.com` publishes **`llms.txt`** (172 KB, a page index *and* a chapter listing every
endpoint by method and path) and **`llms-full.txt`** (8.2 MB, the documentation set as one file). The
previous run knew `llms.txt` existed — its own notes name it as where the 13 page paths came from — and
read it as a list of page paths. The endpoint chapter is 450 lines further down the same file.

One fetch of that index would have answered this run's blocking question.

The rendered catalog pages remain unreachable; every form tried returned the same 65475-byte HTML shell
with a `200`, exactly as the previous run documented. But the material they render is in the full-text
dump, and `usd-futures/api-reference.md` in this snapshot is the extract.

## Does anything block running against the exchange?

**One thing, and only for one family of orders.** The five conditional order types cannot be placed
through `POST /fapi/v1/order` and will not be until the connector moves to `/fapi/v1/algoOrder`. That
blocks 5f's fourth stage.

Everything else is open. The position open/close path, limit and market placement, modification,
cancellation and the read paths were all proven live on 2026-09-18 and nothing found here contradicts
them. The two silent `changed` rows — `avgPrice` and `-1008` — degrade quality rather than prevent
operation, and the two defects of our own are bounded in the way recorded above.

## Gaps this run did not close

**One, reduced from two.** The nested payloads of the user-data-stream events remain `unretrievable`:
`ORDER_TRADE_UPDATE`'s order object, `ACCOUNT_UPDATE`'s entries and now `ALGO_UPDATE`'s payload all
render through a `<SchemaEmbed>` component whose schema is in neither index file. The ~20 short field
names this module reads are still verified against nothing.

The futures REST **response** schemas were the other gap and are partly closed: the per-endpoint
reference gives operation descriptions, and the integration notice gave the one answer that mattered.
Full response schemas remain out of reach, which is why the algo endpoints' responses are recorded as
unknown rather than guessed.
