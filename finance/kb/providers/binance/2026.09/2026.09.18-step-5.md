## What was there at the start

The connector's offline half was covered by nothing: not a line of `WebSocketService`, `BookTickerService`,
`ListenKeyResolver` or `UserStream` was executed by an offline test. They were reached only by live tests
asserting that a ticker arrived — which says nothing about resubscribe, unsubscribe, a dropped connection,
or a payload that does not parse.

The cause was instrumental: `Annium.Finance.Providers.Tests.Lib` had `TestBaseHttpServerExtensions` and no
websocket equivalent, which is to say there was no server side of a socket — and that is the only place a
stream's contract can be observed from.

## 5a — the missing fixture

`Infrastructure/TestBaseWebSocketServerExtensions`: `this.RunWebSocketServer()` returns a
`TestWebSocketServer` that **hands out connections in turn** (`WaitConnectionAsync`), and a
`TestWebSocketConnection` that reads the frames the service sent (`WaitMessageAsync`, `Received`), sends
frames back (`SendAsync`), drops the connection on purpose (`Drop`), and exposes the URI the client
connected to (`RequestUri`).

Connections are queued rather than passed to a callback: the properties worth pinning here are about the
*sequence* of connections. A client that reconnects produces a second one, and the test's assertion is
about what arrives on it.

The other fixture 5a listed — offline HTTP for the commands — turned out not to be needed for
`ListenKeyResolver`: it builds its requests through `IHttpRequestFactory`, and the existing `RunHttpServer`
with a scripted response is enough.

## 5b — the streams, offline

20 tests in three files: `BookTickerServiceTests` (9), `ListenKeyResolverTests` (6), `UserStreamTests` (5).
Subscribe; subscribe to new topics only; unsubscribe and stop tracking; resubscribe after a drop; a ticker
delivered; a payload that does not parse; a drop reported as `Connecting`; teardown; a failed send. Then:
key fetched, key confirmed, key changed, a failure before the first key and after one, teardown mid-flight.
Then: the socket opened on a key with that key in the URL, closed on a reset, a new key asked for after a
drop, a message forwarded, teardown.

### Three defects found by the fixture's very first run

**1. "Connected" was reported before the resubscribe.** `HandleConnected` called `Connected()` first and
sent the tracked topics after. A subscribe issued on that signal raced the resubscribe, and the same topic
went out twice. The exchange tolerates it, so nothing ever complained. `Connected` is now reported last and
means "connected and resubscribed" — which is also what makes the tests deterministic: waiting for the
server to accept the socket is not enough, the client finishes its handshake later.

**2. The topic set was a bare `HashSet` under two threads.** Written from the caller's thread on every
subscribe and from the socket's thread on every reconnect. Guarded now.

**3. A frame that did not go out was invisible.** `SendTextAsync(...).GetAwaiter()` — the result was never
observed. Decided: **a control frame that fails to send is reported on the error channel**, because that is
the only place a consumer can see it. The exception is teardown: there a failed send is expected, the
reporter is already unbound, and reporting is not merely noisy but throws. Hence the `_isDisposed` flag and
the `catch` around the whole body for the race the flag cannot close.

The send is still not awaited by its caller: subscribing is synchronous, and on a reconnect it runs on the
socket's own thread, which must not be blocked. What is observed is the result, not the call.

### A fourth defect: a changed listen key left the timer in keep-alive cadence

The failure branch beside it switched the timer back to fetch cadence; the changed-key branch did not. So a
key that came back different raised `reset` — closing the stream — and then waited a full keep-alive period
before asking for the replacement. On Binance that is half an hour with nothing connected.

Decided: **a changed key leaves the resolver in exactly the state it was in before its first key, timer
included.**

Worth recording separately, about the test: it catches the defect only if the two intervals differ. In its
first form both were 50ms, and it passed against the unfixed code. It now asserts the cadence the resolver
returns to, and was checked against the unfixed branch.

## 5c — the order lifecycle, offline

15 tests over a connector built by hand against a local server: `UserConnectorCommandTests` (10),
`UserConnectorIngestionTests` (5), plus the `UserConnectorOfflineTestBase` fixture with fakes for the
loaders, the stream, the rate limiter and the signature service. The last is not a convenience: resolving
the real signature service starts a server-time poller against the exchange from its constructor — the one
way an "offline" test quietly reaches the network.

Pinned: all five commands refusing while disconnected without a single request; leverage floored to a whole
number; a cancel whose query does not build never leaving the process and reloading nothing; a modify of a
non-limit order going out as a cancel plus a fresh placement; the reload asymmetry — context on every
outcome, orders only on failure. Ingestion: every message reloads the context, a fill asks for the symbol's
trades and a placement does not, a living order is written as a change and a finished one as a deletion,
and the stream going up and down starts and stops the loaders.

**Two behaviours were first pinned as they stood, then decided by the owner:**

1. `SetLeverageAsync` returned `Ok` whatever the exchange answered — as its own XML doc said it would.
   **Decided: a refusal reaches the caller.** And beyond that: the response carries the leverage that was
   applied, so "accepted and not applied" is refused by the connector **itself**, comparing what came back
   against what was asked. To anything reading the status alone such an answer is indistinguishable from
   success; the synthetic refusal is what makes the two distinguishable. The shape is worth checking on
   every command of every venue: an answer that carries the resulting state is worth comparing against the
   request.
2. **Decided: a modify of a Limit order into a Market order stays refused.** Routing it to
   cancel-and-reinit would mean a caller asking to amend an order and silently getting a new one — at the
   back of the queue, and at whatever the market has moved to.

## 5d — registration and configuration

Both of the skill's checks found drift.

**Ownership.** The futures factory built a listen key resolver and a user stream and added neither to the
disposable box. The connector only unhooks their events, so after its teardown what was left behind was: a
socket still reconnecting; a keep-alive still going to the exchange; and two targets still bound to the
monitor — after which the monitor could never read connected again. Both are in the box now, the stream
first, so it is torn down before the resolver it listens to.

**Endpoints.** Drift in both directions: spot kept `/ws/` and `/stream` inline in its mapping profiles
while futures kept both in `Endpoints`, and futures kept `/fapi/v1/listenKey` inline in its factory. All
three moved into `Endpoints`.

Neither of those two checks has an offline test behind it and cannot have one: the factory resolves real
endpoints, so building a connector through it reaches the exchange. What a test does cover is the third
part — every key a venue registers under resolves (`ProviderRegistrationTests` on both venues), including
the stream payload keys that have no HTTP factory of their own and would be missed by a sweep through
those.

## 5e — live, read-only

Run twice against the real exchange on 2026-09-18, with credentials: **21 tests, 15 passed, 6 skipped,
none failed**, both times. The six skipped are spot's `UserProviderTests`, marked `Not implemented`, which
is about those tests rather than about access.

What 5e added is the test that was missing rather than a re-run of what existed. Every live user test on
this venue trades, so they live in the write block and are approved one at a time — and the question that
comes before all of them, *does the connector connect at all against the real exchange*, could not be
asked without approving a trading run. The write base actively manages the account around each test:
cancels open orders, closes positions.

`UserConnectorReadTestBase` places nothing, cancels nothing, closes nothing. Reaching connected is the
assertion rather than a step before it: for a user connector it means a listen key was fetched from the
exchange, a websocket opened on it, and every loader behind it reported in. The account snapshot arriving
and the error channel staying silent are the rest.

It failed on its first live run, and the failure was the test's: `No keyed service for type
IUserConnectorInstanceFactory` — a derived live test registers its venue through `RegisterProvider`, and
this one did not. Worth recording because the failure looks like a connector defect and is not: the
connector was never built.

## Found along the way and fixed here

`CompositeLoaderTests.StopPreventsFurtherRequests` flaked in Release: `attempts (2) != 1`, and the failure
said nothing about `Stop`. The fast interval is the retry period, not a delay before the first fetch:
`Start` fetches at once and repeats on that interval until a fetch succeeds, stopping the timer only then.
At 1ms the retry landed before the success was observed. The two tests that assert an exact count now use
an interval no retry can fire inside; five Release runs of the class, clean.

One of this run's own 5b tests flaked once too: `Subscribe_FailedSendReachesTheErrorChannel` took the first
error off the channel, and after the server is closed the reconnect refusals go to the same place. It now
reads until it finds the one it is about.
