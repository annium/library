**Date:** 2026-09-21. **Branch:** `feature/binance-spot-assessment`. **Contract:** `manifest.md` §10, §11.

The report is immutable: it describes a run, not the current state. The living state is in `status.md`.
It follows [the offline half](2026.09.21-step-5-spot.md) and [the trading block](2026.09.21-step-5-spot-trading-block.md).

Approved by the account holder, who stated the account: no open positions, 34 USDT, and DOTUSDT as the
instrument to trade. Both stages were run.

## Result

- **Read block: 22 of 22, nothing skipped.** The spot user connector reached connected against the real
  account for the first time — which on this venue means the socket opened against the WebSocket API and
  a signed subscription was accepted. The new transport works.
- **Trading block: 4 of 4, run twice, clean both times, the account left with nothing open.**

Getting there took four fixes. Three were defects and one was a test that passed for the wrong reason.

## What the live runs found

### 1. The contract predicted the rate exhaustion and the test config walked into it anyway

The first trading run was killed part-way, and every request after it was refused by the local limiter
before it was sent. The cause was in the manifest already, in §10, written three days earlier:

> an unscoped open-order list costs 80, and a one-second reload of it is 4800 a minute against a ceiling
> of 6000 — the whole allowance for one list

The live test configuration set a one-second scheduled reload, copied from the venue where that list
costs half as much. **A fact recorded in the contract and ignored in configuration is not a fact that
protects anything.**

The fix separates the two things the loader config conflates: the **scheduled** reload, which is what
runs when nothing is happening and is now 5 to 15 seconds, and the **debounce**, which is what a command
or a stream event triggers and is still 100ms. The tests never depended on the schedule; they depend on
the debounce, and they still do.

### 2. Cancel-all is answered with the orders it cancelled, not with an acknowledgement

**The defect with the worst failure mode of the four.** `DELETE /api/v3/openOrders` answers an array of
the cancelled orders. The connector read it as the `{code,msg}` envelope the other venue answers with, so
it failed to parse — and reported a **failure to the caller for a cancellation that had already
happened**.

A caller told a cancel-all failed does one of two things, and both are wrong: retries it, which on the
now-empty book is refused; or believes orders are still open when they are not.

Fixed, and pinned offline against the venue's own answer recorded off the wire. One honest limitation:
the serializer's element converter is **not** independently pinned — the connector discards the payload,
so removing the converter changes nothing a test can see, and a mutation confirmed it survives. What is
pinned is the response type, and reading the array as an envelope kills the test.

### 3. Cancel-all is refused on a symbol with nothing open — and the code does not say why

Measured: HTTP 400, the code the reference calls `CANCEL_REJECTED`, message "Unknown order sent."

The tempting fix is to fold that code into success, and it is wrong. The same code carries "Market is
closed.", "This account may not place or cancel orders." and "This symbol is restricted for this
account." — **the reason is in the message, not the code.** Folding it would swallow, in a cleanup path,
the two failures a cleanup path least wants swallowed.

So the fixture asks only when there is something to cancel. That required distinguishing an empty
snapshot from a snapshot that has not arrived, which look identical from a queue that neither populates.

### 4. A distance chosen for safety was refused for being safe

Every order the block places is priced far below the market so it cannot fill. Half the market was
refused outright: `PERCENT_PRICE_BY_SIDE` bounds how far a limit order may be priced *from* the market,
so the distance is bounded from **both** sides.

Three things made that failure exact rather than marginal, and only the first is obvious:

- the bound was **exactly** half;
- it applies against an **average of recent trades**, not the bid the price was computed from, so
  dividing the bid by the bound's own factor lands on the wrong side whenever the average is above it;
- rounding down to the tick — the safe direction for not filling — is the unsafe direction for this.

The bound is not in `InstrumentModel`: the provider reads the price, lot, notional and order-count
filters and drops this one. So it cannot be computed, only left room for. That gap is recorded rather
than papered over.

### 5. A test that passed for the wrong reason

`AnOrderBelowTheMinimumNotional_IsRefused` passed on the first run — while the venue was refusing *every*
order in the block for the price filter above. A test that asserts only "it was refused" passes on any
refusal. It asserts the notional now because the price it uses is valid; before, it asserted nothing in
particular and reported success for it.

## Two things this run did not establish

**The futures account was not verified.** The first trading run was launched through the recipe that
selects the write block across the whole solution, which includes the other venue's trading tests, and it
was killed part-way. Every run after it was filtered to this venue. An attempt to confirm the other
account is flat did not succeed: response bodies are not logged on read paths, so the check proved
nothing and is reported as unproven rather than as passed.

**A fill is still not asserted live.** Nothing in this block fills, by design, so the trade a fill
publishes, its commission, and a partially filled order's arithmetic remain pinned offline only.

## Outcome

Finance tests 576 → **577** offline. Read block 22/22. Trading block 4/4, twice, account clean after each.

Four facts moved to `live` in §11 and none of them came from the documentation: the transport works with
an HMAC key, cancel-all answers a list, cancel-all is refused on an empty book under an ambiguous code,
and the price filter bounds the safe distance.
