# Binance spot — step 4: the read paths, market half

**Date:** 2026-09-21. **Branch:** `feature/binance-spot-assessment`. **Contract:** `manifest.md`.

The report is immutable: it describes a run, not the current state. The living state is in `status.md`.

This closes the three market-side items the assessment listed. The user half of step 4 is untouched and
remains the gate: those four read paths do not exist.

## What was closed

**The candle request was pinned by one parameter out of four.** Only the cursor was asserted, because
the paging test needed it and nothing else needed anything. That left symbol, interval and page size
free to be wrong — and a mutated symbol fetches another instrument's candles and still returns a full
page, which is exactly what the caller expected to see. All four are asserted now, each
mutation-checked.

**Neither path was asserted as the server received it.** The local test server answers whatever it is
asked, so a typo or a wrong version is invisible offline and surfaces only against the venue. This
provider has already lost a live run to precisely that — a path pinned at a version the exchange had
moved on from, agreed upon by every offline fixture and by the code, and wrong about the world. Both
paths are asserted now, both mutation-checked.

**The candle failure path was unverified.** Its success type is a collection, which is the shape that
used to swallow an exchange error and hand the caller an empty list. The futures venue re-pinned that
at its own call sites after the upstream fix; this path never was.

## Two things the run learnt rather than confirmed

Both were wrong assumptions of mine, and both are now written into the tests that caught them.

**A refusal is not free of consequences.** The first version of the failure test drove a refusal and
then a success through one provider. The second answered `TooManyRequests` — from the *local* limiter,
which the refusal had stood down, without the server hearing about it. The limiter was doing its job;
the test was asserting the wrong thing. Each provider gets its own limiter now.

Worth keeping: the cause was visible only because the assertion printed the status rather than a
boolean. A test asserting `IsNot(Ok)` would have gone green on the refusal and red on the success with
nothing to say about why.

**"Empty answer" and "empty batch" are different things here.** The assumption was that a window the
venue answers with no candles yields a batch carrying an empty collection. It yields **no batch at
all** — the iteration simply ends. A refusal, by contrast, yields one carrying a status.

So the two outcomes are distinguishable, which is the property step 4 asks for, but not in the shape
assumed. The test now asserts what the code does, and says so.

## What could not be mutation-checked, and why

The refusal half has no local mutation: the discarding it guards against lived upstream and is fixed
there, so there is nothing in this repository to break. The test is a regression guard over that fix.
Stated rather than counted as a kill.
