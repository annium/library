# Binance spot — step 5: the connector, offline

**Date:** 2026-09-21. **Branch:** `feature/binance-spot-assessment`. **Contract:** `manifest.md` §10, §11.

The report is immutable: it describes a run, not the current state. The living state is in `status.md`.

This is the offline half of step 5. **No live stage was run**, and none is approved — the trading block
does not exist for this venue and creating it is its own gate.

## What the step found before it wrote anything

The connector skill's first task is checking that the contract covers what is about to be ported. It did
not, and collecting the rest produced the finding the whole step turns on: **this venue's account stream
is reached by a signed method call on a request/response socket, not by a key spent in a URL.** The key
mechanism is deprecated and its documentation removed — `listenKey` and `userDataStream` have zero
occurrences in the REST reference.

That is recorded in `manifest.md` §11 with its citations. What it meant for the work: the component that
carries the account stream could not be ported. It had to be written.

## What was built

**A WebSocket API request builder.** The protocol is request/response: a frame carries an id the reply is
matched by, a method, and parameters. Signing it differs from signing a REST request in two ways, both
invisible afterwards because a wrong signature is refused without naming a parameter — the payload is
sorted by name rather than composed in order, and values go in raw rather than percent-encoded.

**A second implementation of the account stream**, alongside the listen-key one. It opens the socket,
sends a signed subscription, and reports itself connected **only once the venue acknowledges it**. It
resubscribes on reconnect, resubscribes without reconnecting when the venue ends the subscription and not
the socket, retries a refusal rather than tearing down a healthy connection, and unwraps the transport
envelope so that both implementations hand a consumer the same thing.

**The connector itself**, which was five `NotImplementedException`s. Placement, replacement, cancellation,
cancel-all, the sync cycle, and the ingestion of both account events.

## The config that had to move first

`UserConfigBase` required a listen-key path and a listen-key cadence from every venue, including the one
that has neither. Both moved to the venue that uses them. The spot module had been filling them with
values nothing resolved — registered machinery for a mechanism the venue had stopped documenting, which
cost nothing only because the connector was never written.

## Decisions worth naming

**A replacement is one request, not a cancel and a placement.** The venue offers a cancel-and-replace
evaluated as a unit, sent with the mode that stops if the cancel fails. Expressed as two requests, a
cancel that succeeds and a placement that does not leaves the account with neither order and the caller
with a failure that does not say so.

**It is not called an amendment, because it is not one.** This venue's amend endpoint reduces quantity
and nothing else, so a change of price loses the order's place in the queue however it is expressed.

**Setting leverage is refused rather than thrown or accepted.** An exception makes a caller that works
across venues special-case this one. A success is worse than either: a caller told its leverage was
applied sizes the next position against a number the account has never heard of.

**A trade is published by the reload, not by the stream event** — even though this venue's order event
carries the fill's price, quantity and commission, which the neighbouring venue's early fill notice does
not. One source rather than two: published from both, every fill reaches a caller twice, and the
deduplication that would then be needed is a worse thing to get wrong than a reload is to wait for.

## A defect in existing code, found while wiring it

`BuildModifyOrderQuery` set a time in force unconditionally, including on market and market-triggered
types the venue does not accept it for. Three tests asserted that as correct. Fixed, and the three
rewritten to assert its absence.

## Mutation checking: thirteen mutations, and the two tests it caught

Every fact claimed as pinned was broken and the break watched. Thirteen mutations across the three
components; **all thirteen killed** in the end, but three of them only after something was fixed first.

**Two mutants did not compile,** and both were caught by reading the build result before the test result
— given `--no-build` the runner reports the previous binary as green, which certifies a test that guards
nothing. Removing a guard made a method unused and the analyser refused it; removing a constant's only
use did the same. Both were re-run as value changes rather than deletions, and both then died.

**Two tests were vacuous and passed anyway.** These are the run's most useful output, because each looked
like ordinary coverage:

- A test asserting that a reply carrying the wrong id is not taken as the subscription **raced its own
  send**. Sending a frame returns when the bytes leave, not when the other side has read them, so the
  status was read before the frame could have changed it — and the assertion held whatever the stream
  believed. Rewritten to assert what the stream *does next*: an unacknowledged subscription produces a
  retry, and a stream that took the wrong reply sends none.
- A test asserting the ended-order notes are bounded **did not discriminate the bound**. It checked that
  the oldest note was dropped, which a cap of one does as well as a cap of a thousand. Rewritten to assert
  an id from inside the window as well as one from each end, which is what tells the two apart.

Both were found by a mutation surviving, which is the argument for mutating the value rather than only
reading the test.
