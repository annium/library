# Spec: what a connector costs per value, and what it should

## Scope

The finance connector stack — `Annium.Finance.Providers.Core` and the Binance providers built on it —
measured and reworked as the path a value takes from a socket to a consumer. crypted's backtest sits on the
same stack and is the load that exposed most of this, but its own remaining work is a separate spec.

Two of the items below are **done** and shipped; the rest are proposed and ordered.

## What is already measured

| where | condition | figure |
|---|---|---|
| `key` host, 58 instruments, no ticker subscription active | at rest | 156 KB/s allocated, 0 gen0 GC in 45 s, 7 timers, 3.8 pool items/s, 118 MB working set |
| `unit` host, one live account | at rest | 0.6 MB/s allocated, 16–20 timers, 18 pool items/s, 145 MB working set |
| tester, one backtest through the replay connectors | under load | 745 MB/s allocated (~71 KB per simulated step), 3.4 gen0 GC/s, 3.3 % of wall in GC pauses, up to 2.0 GB working set |

The live figures are *at rest*: no ticker stream was flowing while they were taken, because a subscription
only exists while a trend decision is open. **The per-message path has been read, not measured.** Anything
below that concerns it is reasoning about code, and says so.

## Done

### 1. Delivery is a property of what feeds the connector

`ConnectorDelivery.Buffered` hands values to a background pump; `Inline` delivers them on the writer's
thread, before the write returns. Both bases take it as a required argument, and `ConnectorChannel.Create`
is the single place that turns it into a channel.

A live connector is `Buffered` because its values arrive from a socket, on a thread it does not own and
must not block. A replay connector is `Inline` because it produces its own values and gains nothing from a
handoff — and because "delivered" then means "the write returned", which is what let crypted's backtest
delete a counting protocol and three thread transitions per step.

### 2. Log arguments no longer cost anything when the level is off

The log methods check the level, but C# evaluates their arguments first. `LogConfig.IsEnabled` lets a call
site whose arguments cost something ask first, and the repeating sites now do: the UsdFutures user
connector decoded every account-stream message to a string; `BookTickerService` copied and decoded every
payload it could not parse; `StatusMonitor` built a description of every target on every status report;
`WebSocketService` joined the topic list on every subscribe, unsubscribe and reconnect.

`StatusMonitor.TrackStatus` also returns early when a target reports the status it already has — the
aggregate cannot have moved, and loaders report their state on **every poll**, so that is the common case.

Outside finance but on the same path: `ExecutorBase` built an id string per scheduled task and per task run
— and a sequential executor backs every `DoSequentialAsync`, so "per task" is "per value" on some streams.
Two of those calls also had `Interlocked.Increment(ref _taskCounter)` sitting in their argument list, where
a guard would have stopped the counter advancing; the increment is now hoisted out, which it should have
been regardless of logging.

## Proposed

### 3. One channel, not two

`BufferedChannel` is a source channel, a pump, a target channel, and `AsObservable().Publish().RefCount()`.
Two buffers and two consuming loops where the point is one thread handoff.

The second channel exists because both bases take a permanent keep-alive subscription
(`Disposable += Tickers.Subscribe()`, and three more in the user base). With `RefCount`, that subscription
starts the reader at construction, so anything written before the sync cycle connects would drain to
nobody. Hold the values in the source channel and the problem goes away — which is what the pair does.

Replace with: one channel, one pump, a `Subject<T>`. `Connect()` starts the pump; disposing it stops the
pump without completing the subject, because the sync cycle connects again on every pass. Writes before
the first `Connect()` accumulate in the channel exactly as they do now. The keep-alive subscriptions are
deleted — a subject needs no subscriber to stay alive.

Per user connector: 8 channels and 4 pumps become 4 channels and 4 pumps. Observable semantics are
unchanged: multicast, and a late subscriber gets no history.

**Risk to watch.** `Connect()` runs on every sync cycle and `_sourceSubscriptions` is disposed and *reset*
each time — the same place a disposal-during-sync race was fixed before. `DisposalDuringSync_LeavesNothingSubscribed`
is the test that must stay green, and it is the reason this is its own change rather than part of a larger one.

### 4. A bound, and a way to see the queue

Both channels are unbounded. A consumer that stalls grows memory without limit, adds latency, and says
nothing. That is the wrong default for a stream fed by an exchange.

The right policy differs by stream, and pretending otherwise is what produces one bad compromise:

- **Tickers** — only the latest matters. Bounded with `FullMode = DropOldest`, plus a count of what was
  dropped, surfaced once when dropping starts and periodically after, not per value. Memory becomes
  bounded and a consumer that cannot keep up becomes visible instead of invisible.
- **Assets, positions, orders, trades** — these are `ChangeEvent`s; losing one corrupts the consumer's
  state. Dropping is not available, and blocking would stall the socket. They stay unbounded, and gain a
  depth watch: a warning when the queue passes a threshold, so a stall is loud rather than silent.

Capacity and threshold belong in the provider configuration, with defaults.

### 5. Then measure the per-message path, properly

Only after 3 and 4, and only with real load. Two ways, in order:

1. An offline benchmark over the recorded payloads the provider tests already carry — gives the cost of
   deserialization and delivery per message without touching the exchange.
2. A live read-only run with a ticker subscription actually open, sampling the same counters as the table
   above.

Until one of those exists, no claim about the per-message cost belongs in this document.

## Not in scope

- crypted's backtest allocation (~71 KB per step) — the same stack, but the allocations are the strategy's
  and the matching engine's, not the connectors'. Its own spec, and it starts with a `dotnet-trace`
  allocation profile rather than with reading.
- `Task.WhenAny(work, Task.Delay(100))` without cancellation in crypted's `OrderExecutor` — 1051 live
  timers during a backtest against 1 at rest. crypted's change.
- The logging pipeline itself — `BackgroundLogScheduler`'s single reader and `ConsoleLogHandler`'s
  process-wide lock cost a parallel pair of backtests 67 % of wall time at `trace`. Real, measured, and a
  change to `Annium.Logging.*` rather than to finance.

## Acceptance

For 3 and 4: the full library suite green (currently 3929 tests), `DisposalDuringSync_LeavesNothingSubscribed`
included; crypted's backtest results unchanged to the last digit against its recorded baseline; and the
`unit` host's at-rest allocation rate no higher than the 0.6 MB/s above.
